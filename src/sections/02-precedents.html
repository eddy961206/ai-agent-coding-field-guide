방법 자체를 제품과 스킬로 만든 선례

pstack — 검증 가능한 환경을 만드는 스킬

가져올 점 앱 사용 경로를 아는 검증 스킬, 반복 실수 교정, 상태도와 형식 기법의 구분.

적용 조건 프로젝트별 권한과 검사 범위를 먼저 맞춰. 여러 스킬의 효과가 자동으로 합산되지는 않아.

[[pstack|원본]] [[2118425409276801121|검증의 구분]]
Superpowers — 요구 확인부터 완료 검증까지

가져올 점 설계를 이해한 뒤 작고 검토 가능한 작업으로 나누고 완료를 증거에 연결하는 절차.

적용 조건 인터뷰·계획·TDD·여러 에이전트가 작은 수정에는 부담일 수 있어. 저장소 정책에 맞춰 선택해.

[[superpowers|원본]] [[reddit-overhead|작은 작업의 부담]]
Compound Engineering — 다음 작업이 더 쉬워지게

가져올 점 요구 탐색 → 계획 → 구현 → 단순화 → 검토 → 배운 점 기록. 해결한 문제를 다음 계획의 근거로 되돌려.

적용 조건 재사용할 지식이 있는 작업에서 가져와. 매번 모든 단계를 거치는 비용은 따로 살펴야 해.

[[compound|원본]] [[reddit-combined|결합 사용 경험]]
Matt Pocock의 Skills — 작은 능력을 조합하기

가져올 점 요구와 용어를 맞추고 명세에서 의존성 있는 티켓으로 연결하는 방식.

적용 조건 의존성과 완료 기준을 먼저 가져오고, 인터뷰와 전체 절차는 작업 규모에 맞춰.

[[matt-pocock-skills|원본]]
Spec Kit — 명세를 실행과 확인에 연결

가져올 점 제품이 해야 할 일과 이유를 명세에 두고 계획·작업·구현으로 연결. 현재 문서는 버그 수정과 아이디어 평가도 별도 진입점으로 다뤄.

적용 조건 명세 자체가 사용자 의도에 맞는지 검토해야 해. 명세 문서가 구현 정확성을 보장하지 않아.

[[spec-kit|원본]]
OpenSpec — 변경 단위의 명세와 보관

가져올 점 변경을 제안·요구사항·설계·작업으로 묶고 완료된 변경을 보관하는 구조.

적용 조건 현재와 앞으로의 동작을 분리하기 좋아. 실제 코드와 다른 명세가 남지 않게 관리해야 해.

[[openspec|원본]]
Agent OS — 프로젝트 규칙을 필요한 곳에

가져올 점 코드의 규칙을 발견·색인하고 해당 작업에 관련된 규칙을 제공하는 방식.

적용 조건 잘못된 기존 패턴까지 표준으로 고정하지 않게 검토해. 모든 지침을 항상 읽힐 필요는 없어.

[[agent-os|원본]]
GSD Core — 단계별 상태와 새 맥락

가져올 점 결정·계획·실행·검증·출하를 구분하고 상태 파일로 세션을 이어가는 방식.

적용 조건 새 맥락과 병렬화의 비용도 고려해. 조사 당시 이전 저장소는 open-gsd/gsd-core로 이동을 안내했어.

[[gsd|현재 저장소]]
Ralph Playbook — 새 맥락에서 한 일을 반복

가져올 점 요구사항·계획·실행을 분리하고 결과를 파일과 Git에 남겨 다음 반복으로 이어가는 구성.

적용 조건 종료 조건과 예산을 먼저 정해. 무제한 루프나 고정 토큰 사용 비율을 보편적인 최적값으로 가져오지 않아.

[[ralph-guide|플레이북]] [[ralph-original|초기 글]]
autoresearch — 고정된 평가로 실험 비교

가져올 점 수정 범위·평가 코드·실행 예산·지표를 분리하고 결과로 변경을 유지하거나 버리는 흐름.

적용 조건 원본은 단일 GPU 학습 실험이야. 제품 개발 전체가 아니라 성능 실험처럼 기준을 고정할 수 있는 작업에 참고해.
