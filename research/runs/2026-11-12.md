## OpenSpec 2.0의 적용 조건 변화

- [OpenSpec 1.17.0의 릴리스](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.17.0)는 11월 10일 KST에 2.0에서 `/opsx:*` 명령 파일을 제거하고 스킬을 유지할 계획이라고 예고했다.
- 이후 나온 [2.0.0 릴리스](https://github.com/Fission-AI/OpenSpec/releases/tag/v2.0.0)는 11월 12일 07:41:44 KST다. 명령을 제거하고 스킬을 `.agents/skills/`에 공통으로 두며, 이 경로를 읽지 않는 Claude Code와 Kiro에는 링크를 제공한다고 설명한다. `/opsx:propose` 대신 `/openspec-propose`, Codex에서는 `$openspec-propose`를 예로 든다. 워크플로 자체는 바뀌지 않았다고 한다.
- 릴리스 노트는 이전 위치의 수정한 생성 파일은 보존·표시하지만 공통 `.agents/skills/`에서 직접 수정한 스킬은 `openspec update`가 덮어쓴다고 별도로 경고한다. 업데이트 전 수정분을 보관하고 `openspec update --dry-run`을 확인하는 제안은 이 경로 차이에 근거한다. 실제 업데이트·파일 보존과 링크 동작은 실행해 검증하지 않았다.

## 파일 작업 분리와 접근 경계

- 11월 8일 KST의 [Codex 이슈 #60189](https://github.com/openai/codex/issues/60189)는 Linux의 Codex CLI 0.166.0에서 에이전트가 상위 디렉터리의 지침 파일을 재귀 검색해 형제 worktree까지 탐색하려 했다는 사용자 보고다. 다른 환경에서는 외부 접근 경계가 검색을 거부했다고 한다. 다른 worktree의 지침이 실제로 적용됐는지, 모든 버전에 영향을 주는지와 수정 여부는 확인하지 못했다. 확인 시 이슈는 열려 있었다.

- 11월 12일 KST의 [파일 잠금 베타 제작자 글](https://www.reddit.com/r/ClaudeCode/comments/1xtwbw1/i_made_claude_code_file_locks_for_shared_projects/)은 같은 프로젝트의 Claude Code 세션이 변경 전 훅으로 파일 잠금을 공유하고 Codex는 승인 경로로 같은 잠금을 사용한다고 주장한다. macOS Apple Silicon 전용이고 체험 후 유료다. 실제 설치, 여러 PC의 동작, 잠금 우회·중단 후 해제를 검증하지 않았다. 별도 worktree나 파일 잠금이 모든 경로의 파일 접근을 제한한다고 가정할 수 없다.
