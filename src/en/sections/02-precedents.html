People already doing similar work

Resource collections and execution tools serve different purposes. This comparison covers structures and methods found in their documentation, not performance tests of every tool.

Methods packaged as products and skills

pstack — skills for an environment that supports verification

What to borrow Verification skills that know how to use the app, correction of recurring mistakes, and distinctions between statecharts and formal methods.

Conditions Align permissions and verification scope with the project first. Combining skills does not automatically combine their benefits.

[[pstack|Original]] [[2118425409276801121|Types of verification]]
Superpowers — from clarifying requirements to verifying completion

What to borrow Understand the design, break work into small reviewable tasks, and connect completion to evidence.

Conditions Interviews, planning, TDD, and multiple agents can be costly for small changes. Choose according to repository policy.

[[superpowers|Original]] [[reddit-overhead|Overhead on small tasks]]
Compound Engineering — make the next task easier

What to borrow Explore requirements → plan → implement → simplify → review → record lessons. Feed solved problems back into future planning.

Conditions Use it where there is knowledge worth reusing. Assess the cost of going through every stage each time.

[[compound|Original]] [[reddit-combined|Experience combining tools]]
Matt Pocock’s Skills — combine small capabilities

What to borrow Align requirements and terminology, then turn specifications into tickets with explicit dependencies.

Conditions Start with dependencies and acceptance criteria. Scale interviews and the full procedure to the task.

[[matt-pocock-skills|Original]]
Spec Kit — connect specifications to execution and checks

What to borrow Put what the product should do and why in the specification, then connect it to plans, tasks, and implementation. The current documentation also provides separate entry points for bug fixes and idea evaluation.

Conditions Check whether the specification matches user intent. A specification document does not guarantee a correct implementation.

[[spec-kit|Original]]
OpenSpec — specifications and archives for individual changes

What to borrow Organize each change into a proposal, requirements, design, and tasks, then archive completed changes.

Conditions Useful for separating current behavior from intended behavior. Keep specifications aligned with the actual code.

[[openspec|Original]]
Agent OS — project rules where they are needed

What to borrow Discover and index conventions in the code, then provide the rules relevant to a given task.

Conditions Review existing patterns before turning them into standards. Not every instruction needs to be loaded all the time.

[[agent-os|Original]]
GSD Core — stage-specific state and fresh context

What to borrow Separate decisions, planning, execution, verification, and shipping. Use state files to continue across sessions.

Conditions Account for the cost of fresh contexts and parallel work. At the time of research, the old repository directed readers to open-gsd/gsd-core.

[[gsd|Current repository]]
Ralph Playbook — repeat one unit of work in fresh context

What to borrow Separate requirements, planning, and execution. Leave results in files and Git for the next iteration.

Conditions Define stopping conditions and budgets first. Do not treat unlimited loops or fixed token-use ratios as universally optimal.

[[ralph-guide|Playbook]] [[ralph-original|Early article]]
autoresearch — compare experiments with a fixed evaluation

What to borrow Separate the scope of changes, evaluation code, execution budget, and metrics. Use results to keep or discard changes.

Conditions The original concerns single-GPU training experiments. Use it as a reference for tasks with fixed evaluation criteria, such as performance experiments, rather than product development as a whole.

[[karpathy-autoresearch|Original]]
What this guide adopted: Problem-oriented method cards, distinct date types, application conditions, contrasting cases, copyable prompts, original sources, and the document revisions reviewed. It does not ask readers to install every tool.
